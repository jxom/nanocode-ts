- feat(bench): add bench/sla/ci.ts, paired bootstrap verdicts for interleaved SLA runs (2026-11-16, B6b-12 lane). Benchmark lanes compared arms by eye from medians, and no script turned interleaved samples into a verdict. `node bench/sla/ci.ts --arm=nc (--vs=<arm> | --target=<value>) <samples.jsonl>...` reads rows `{round, arm, session, turn, metric, value, t?, build?, match?}` or the rows `bench/sla/run.ts` writes (`index` is the round, `lane` the arm, every numeric key a metric, `ready` only on turn 1, `wall` the order, an `error` row a failed round). For each metric and turn (or all turns with `--pool-turns`) it prints p50 and p99 per arm with linear (numpy default) quantiles, the ratio of medians, the ratio of p99s and the median of per-round median ratios, each with a 95% percentile bootstrap interval: 10,000 resamples (`--resamples`) of whole rounds with a fixed seed (`--seed`, mulberry32), where rounds that share a session are merged into one cluster and resampled together, and both arms of a round always travel together. The verdict follows the paired round ratio: WIN when its interval excludes 1 on the better side (`--better`, by default lower, and higher for metrics ending in `tps`), LOSS when it excludes 1 on the other side, and TIE otherwise. A cell is MISSING when it has fewer than 30 complete rounds (`--min-rounds`), a round lacks an arm, failed or has unequal sample counts per arm (`--drop-incomplete` drops such rounds and reports the count), an arm has more than one `build`, the arms have different `match` strings, or the time spans of two rounds overlap (by `t` or `wall`, else by line order). `--json=<path>` writes every cell. Checked on the hosted Hand (Node 24, unpinned and shared, load 180-316) against a separate numpy reimplementation that uses the same generator: points and interval ends match to 1e-9 on 9 synthetic sets (win 0.8x, tie, loss 1.25x, sessions over 2 rounds, rendered_tps, target 800, run.ts rows, each turn). An independent numpy generator gives intervals within 0.4%. An exact 0.8x set gives [0.8, 0.8]. Blocked, line-ordered, unbalanced, mixed-build, unmatched and N=29 sets give MISSING. On 200 null cells (true ratio 1, 30 rounds, 2 turns, 1,000 resamples), 6.0% of paired verdicts, 1.5% of ratio-of-medians intervals and 5.0% of ratio-of-p99 intervals were not TIE. The paired median interval ends fall on order statistics of the round ratios, so a new seed often leaves them in place.

This repository is nanocode-ts (nanocodexyz/nanocode-ts, formerly nanocode-wasm): the nanocode Rust SDK compiled into one WebAssembly module, the TypeScript host that runs it in any JavaScript runtime that can instantiate WebAssembly, such as Cloudflare Workers, Node, Deno and browsers, and TypeScript adapters for Vercel and Cloudflare, so a host repository writes only TypeScript and builds no Rust. Its sibling `../nanocodex` supplies the SDK; `sdk-revision.json` records the SDK master revision this package builds against; check out that revision in the sibling when preparing a fresh workspace. `.github/workflows/release.yml` builds every push to main against the SDK at `sdk-revision.json`, checked out beside it as `nanocodex/`, with the Rust release `rust-toolchain.toml` pins, checks it, packs it and publishes the tarball as the GitHub release `build-<short commit>`. Before that it publishes the WASM build outputs, `dist/nanocode_wasm.wasm`, `dist/interpreter.wasm`, `dist/models.js` and `dist/models.d.ts` with their digests in `dist/nanocode-wasm.json`, as the asset `nanocode-wasm-<fingerprint>.tgz` of the release `wasm-<fingerprint>` (`node scripts/publish-wasm.mjs --upload`), and checks out the SDK and runs Cargo only when that release does not exist yet. `node scripts/wasm.mjs` prints the fingerprint: the first 20 hex digits of a SHA-256 over `sdk-revision.json`, `Cargo.toml`, `Cargo.lock`, `rust-toolchain.toml`, `scripts/build.mjs`, `scripts/wasm.mjs`, the JavaScript files under `src/wasm`, every `src` Rust file and the interpreter's `Cargo.toml`, `Cargo.lock` and Rust files, so a push that changes only TypeScript reuses the last WASM release. `node scripts/publish-wasm.mjs` without `--upload` writes the asset to `output/`, from `dist/` when its manifest names the current fingerprint, or from a directory or a `build-<commit>` tarball given as its argument, which must come from a commit with the same Rust inputs; only builds against the SDK at `sdk-revision.json` may be uploaded, since the fingerprint does not cover `../nanocodex`. Hosts install the tarball, `"nanocode-ts": "https://github.com/nanocodexyz/nanocode-ts/releases/download/build-<short commit>/nanocode-ts-<short commit>.tgz"`, which their lockfile pins with its integrity: nanocodexyz/durable-cloudflare (formerly nanocode-worker) and nanocodexyz/durable-vercel; nanocodexyz/nanocode-site builds the package from a checkout instead. `dist/` is build output, ignored by Git and listed in `package.json`'s `files`, so the tarball carries the compiled JavaScript, declarations and module and installing it needs neither Rust nor a TypeScript build. To consume a change without waiting for its release, a host pins the commit, `"nanocode-ts": "github:nanocodexyz/nanocode-ts#<commit>"` (`npm install github:nanocodexyz/nanocode-ts#<commit>`, which also updates the lockfile; editing only `package.json` leaves an installed git dependency in place). npm clones the commit, installs its devDependencies and runs `prepare`, `scripts/prepare.mjs`: it keeps `dist/`'s WASM outputs when `dist/nanocode-wasm.json` names the commit's fingerprint and their digests match, else downloads `wasm-<fingerprint>` over HTTPS without authentication (`NANOCODE_TS_WASM_URL` replaces the URL with another URL, a `file:` URL or a path), checks its manifest and copies it into `dist/`, and when no such release exists builds the WASM with `scripts/build.mjs` if Cargo and `../nanocodex` are present, or fails naming the fingerprint. It then runs `npm run build:ts` (both `tsc` builds and `scripts/zyzz.mjs`) unless `output/typescript-build-fingerprint` matches the TypeScript inputs, so npm's second `prepare` while packing the clone is free. Website feedback (2026-11-06). `nanocode-ts/feedback` and `nanocode-ts/feedback/server` let any website collect comments on its own elements and turn them into issues on its Tempo gateway app, which the app's agent can work on. The widget follows Amp's feedback widget (ampcode.com/news/close-the-loop), the handler follows tempoxyz/accounts' `Handler.auth` (a fetch handler the site mounts on its own server), and the policy callbacks follow ithacaxyz/porto's `Route.merchant({ sponsor })`.

```
page ──▶ Feedback.mount ──POST /feedback──▶ Handler.feedback (site's server, its Tempo Key)
                                              ├─ kv set issues/<id> in the app
                                              └─ turn on options.agent, if set
```

The site's server is the connection to the gateway: `Handler.feedback({ accept, admin, agent, app, fetch, gateway, identify, key, path, public, repo })` holds the key, so no key reaches a browser and the site's origin needs no proof. Its routes under `path` (`/feedback`):

| Route | Answer |
| --- | --- |
| `GET /feedback` | `{ ready: true, agent, app, wallet }` once `GET /api/keys/me` accepts the key, else 503 `{ ready: false, reason, help }` |
| `POST /feedback` | parses the report (`Issue.parse`), asks `accept({ report, request })`, stores the issue at `issues/<id>`, or `git/<repo>/issues/<n>` with `repo`, with `/v1/kv/set` (`ifVersion: null`, private unless `public`), starts a turn on `agent` with `Issue.prompt`, and answers 201 `{ id, link, agent }` |
| `GET /feedback/<id>` | `Issue.summary`: `at`, `id`, `status`, `resolution`, never the comments or the reporter |
| `GET /feedback/issues` | the issues, 100 a page with `cursor`, when `admin(request)` allows it, else 404 |

An issue is `{ version: 1, id, at, status, resolution, reporter, report }`. Its id is `iss_` with the time in base 36 and 4 random bytes, so kv lists issues in filing order. `reporter` is what `identify(request)` returns, such as the address of an accounts `Handler.auth` session. `Issue.prompt` names the kv key and asks the agent to set `status` (`accepted` or `closed`) and `resolution` when it is done, so the agent closes the issue with its own `kv_set` tool. The handler sets no limits of its own: the gateway's kv refuses a value over 64 KiB and keeps it 90 days (its retention), and the handler forwards the gateway's status and detail. A key check that fails is not cached, so a fixed key takes effect on the next request. `fetch` sends every gateway request when given, for a host that reaches the gateway through a binding: a Cloudflare Worker on the same account as the gateway calls it through a service binding, as gakonst/swarms does.

With `repo`, the board is that repository's issues, the tempoxyz/gateway convention `git/<repo>/issues/<n>` (its AGENTS.md: a repository's issues are kv values with that key, and there is no issues API). The handler takes `n` from the counter value `git/<repo>/issues`, `{ next }`, with a compare-and-swap `kv/set` (`ifVersion` the version it read, or `null` when there is none), and retries only on 409, which means another filer advanced the counter. It then writes the issue create-only, and a 409 there (a number taken by hand) takes the next number. The counter key has no trailing slash, so a list of `git/<repo>/issues/` leaves it out. An issue's id is then `n`, its link `/feedback/<n>`, and the widget reads "Filed as #n". The gateway's kv keeps a value 90 days from its last write, so a board idle for 90 days starts again at 1, and numbers whose issues remain are skipped. Checked against the mock gateway, made atomic like the gateway's single-statement writes: eight concurrent posts took 1 to 8 once each, and after a hand-written `issues/10` with the counter at 10, the next post took 11.

`Feedback.mount({ excerpt, parameter, storage, target })` waits for `DOMContentLoaded` when the page has no `body` yet, as for a script in `<head>` (gakonst/swarms loads it there, and the first version threw on `document.body.append`), and shows nothing until the page opens with `?feedback` (`parameter`) or a report from that origin was sent, which `nanocode.feedback.shown` in `storage` records until Hide. It then asks `target.status()`. If that answers `ready: false`, the panel says "Feedback is not set up" with the reason and its help link, and the launcher reopens that panel instead of picking. The launcher starts picking: a transparent overlay takes the pointer, so the page's links and buttons do not run, and `document.elementsFromPoint` without the widget's host finds the element under it. A click opens a comment form at that element. Each comment gets a numbered pin at its element, New comment picks another, and Send passes the report to `target.send`. `Report.describe` records each comment's note, CSS selector (`Report.selector`: the nearest unique id, then tags with `:nth-of-type`), tag, text cut to `excerpt` characters with `…`, and rectangle, and the report adds the page's title, its URL without `parameter` and the viewport. `Report.prompt` writes them as the numbered list an agent reads. `Endpoint.create({ help, url })` is the target for a handler (`url` `/feedback`): a 404 from `url` reads "Nothing answers at /feedback", and a 503 shows the handler's reason. `Gateway.create({ url })` sends to the gateway's own support route, `POST /v1/feedback`, for the gateway's site.

SQL hosts route each call on the SDK's access mark (2026-11-05, SDK bee3d45e7). The SDK's `Sql::run` carries `SqlAccess`: `SqlStore` and `RowStore` mark their reads `Read` and their format migrations `Schema`, and every other call is `Write`. `WorkerStore` (`src/wasm/store.rs`) sends the mark as the `access` field (`read`, `write` or `schema`) of the `store` and `log` host operations. `AgentRuntime` passes it to `SqlHost.transaction` as an optional fourth argument, so a host written before it gets every call as one transaction, as before. `Sql.create` runs a read without `transactionSync` and reports the mark in each `Observation`. `LocalSql.run` runs a read without `BEGIN IMMEDIATE` and prepares a schema statement outside its statement cache.

Agent sessions survive a restart in the middle of an operation (2026-10-30). A Durable Object reset or a deploy used to end every cell and hand operation in flight: the recovered turn reported the step as interrupted by a host crash with an unknown outcome. Cells: `open` gives `LocalCells` `CellJournals::with_sink(WorkerJournals)` (`src/wasm/journals.rs`), which writes each cell's journal ahead to `nanocode_cell_journals` through the durability `store` (the SDK's points: when the cell starts, before a nested call is dispatched, once the cell has consumed a result and has nothing left to run, when an observer begins and when a cell yields; an update with a header replaces the cell's rows; a retired cell's rows are deleted, and a cell that an `exec` or `wait` observed finish keeps them, marked finished, until the session next starts a cell), and restores the scope's journals when a runtime opens, so the recovered `exec` or `wait` replays the cell and observes it. Hand operations: the Cloudflare App logs every request it sends to a hand (`hand_requests`, keyed by the hand's name and the runtime ID of its catalog, with the request's session and call IDs and a deadline of `REMOTE_TIMEOUT_MS` plus the yield the operation requested, the same bound a live operation has) and stores each reply frame before the executor sees it.
